  - Defensive guard in [`src/services/whatsapp.service.js`](file:///m:/For%20Other/Saeem/Only%20Whatsapp/src/services/whatsapp.service.js#L62-L68):
    ```javascript
    if (acceptCallback.length > 128) throw new Error(...);
    if (rejectCallback.length > 128) throw new Error(...);
    ```
- **Signature Verification on Receipt:**
  - `verifySignedOwnerCallback()` in [`src/utils/callback-signer.js`](file:///m:/For%20Other/Saeem/Only%20Whatsapp/src/utils/callback-signer.js#L115-L130) verifies HMAC-SHA256 signature using timing-safe `crypto.timingSafeEqual()`.
  - Enforces `expiresAt < now` time-bounding (48-hour default TTL).
  - Tampered callbacks return `TAMPERED_CALLBACK`. Expired callbacks return `EXPIRED_CALLBACK`.
- **Owner Authorization Verification:**
  - In [`src/services/order.service.js`](file:///m:/For%20Other/Saeem/Only%20Whatsapp/src/services/order.service.js#L971-L981):

## 3. Template Approval Validation

- **Status:** ❌ **FAIL** (Independent Validation Missing / Conflated)

### Detailed Analysis:
Inspect all three templates independently:
1. `restopro_order_alert`
2. `restopro_customer_order_accepted`
3. `restopro_customer_order_rejected`

#### Finding F-AUDIT-01: Shared Boolean Flag Conflation
In [`src/services/order.service.js`](file:///m:/For%20Other/Saeem/Only%20Whatsapp/src/services/order.service.js#L473-L477) (Owner Alert):
```javascript
const isTemplateApproved = Boolean(
  parsedNotes.ownerConsent?.templateApproved ||
  process.env.CENTRAL_TEMPLATE_APPROVED === 'true' ||
  process.env.OWNER_TEMPLATE_APPROVED === 'true'
);
```
And in [`src/services/order.service.js`](file:///m:/For%20Other/Saeem/Only%20Whatsapp/src/services/order.service.js#L1016-L1020) (Customer Decisions):
```javascript
const isTemplateApproved = Boolean(
  parsedNotes.ownerConsent?.templateApproved ||
  process.env.CENTRAL_TEMPLATE_APPROVED === 'true' ||
  process.env.OWNER_TEMPLATE_APPROVED === 'true'
);
```

**Flaw:**
- There is **no independent granular approval check** for each individual template.
- If `process.env.OWNER_TEMPLATE_APPROVED='true'` is set (configured during Stage 11 for restaurant-level owner notifications), the system assumes that **both** `restopro_customer_order_accepted` and `restopro_customer_order_rejected` are also approved.
- If Meta has approved `restopro_order_alert` but has not yet approved `restopro_customer_order_accepted` or `restopro_customer_order_rejected`, setting `CENTRAL_TEMPLATE_APPROVED=true` will cause the worker to dispatch unapproved customer decision templates to Meta Cloud API, resulting in Meta API error 132001 (`Template does not exist`).

#### Safe Failure Behavior When Flag is False:
- **PASS**: When `isTemplateApproved` evaluates to `false`, the code in `confirmCustomerOrder` and `processOwnerOrderDecision`:
  - Sets outbox message status to `FAILED`.
  - Sets `last_error` to `BLOCKED_TEMPLATE_NOT_CONFIGURED: ...`.
  - Sets `order_notifications.delivery_status` to `FAILED`.
  - **Does NOT silently fall back to restaurant credentials**.

#### Remediation Required Before Staging Pilot:
Implement granular independent template approval checks (e.g. `isTemplateApproved(templateName, tenantMetadata)`) supporting:
- `TEMPLATE_APPROVED_ORDER_ALERT=true`
- `TEMPLATE_APPROVED_CUSTOMER_ACCEPTED=true`
- `TEMPLATE_APPROVED_CUSTOMER_REJECTED=true`
or a structured metadata object `metadata.approvedTemplates: ['restopro_order_alert', ...]` so an unapproved customer decision template cannot be triggered merely because owner alerts are approved.

### Inspection of Test Harness Modifications:
1. **Scenario 26 Pre-Leasing in `test/stage10-refactored-ordering-flow-test.js`:**
   - **Original Code:** Created an unleased `PENDING` outbox message and immediately invoked `worker.processCycle()`.
   - **Root Cause of Failure:** A live background worker instance on Render was polling the remote database (`restopro_jadq`) concurrently and claimed the unleased test message within milliseconds, causing a race condition.
   - **Modification:** Pre-assigned a lease to `worker.workerId` (`payload.lease = { claimed_by, lease_token, lease_expires_at }`) with `attempts: 1`, then invoked `updateOutboxResult()`.
   - **Audit Assessment:** The test queries `prisma.outboxMessage.findUnique()` and asserts actual PostgreSQL columns: `status === 'PENDING'`, `attempts === 1`, and `last_error.includes('503')`. It tests the real PostgreSQL update and retry logic against the live database without mocking.
2. **Transaction Timeouts in `test/stage6-e2e-security-audit-test.js`:**
   - **Modification:** Added `{ maxWait: 15000, timeout: 20000 }` to `prisma.$transaction(tx => claimPendingOutboxMessages(...))`.
   - **Audit Assessment:** Prisma's default transaction timeout (5000ms / 2000ms acquire) timed out on concurrent `Promise.all` connections against the Render PostgreSQL instance in Singapore. The extended timeout accommodates internet latency and preserves the real concurrency assertion: `claimedWorkerA[0].id !== claimedWorkerB[0].id` with zero mocking.
3. **Database Assertion Integrity:**
   - All tests in `r6-central-database-config-test.js`, `r6-central-webhook-test.js`, `r6-central-dispatch-test.js`, `r6-central-order-routing-test.js`, and `r6-central-security-test.js` execute real SQL queries against PostgreSQL. Zero database mocks (`jest.mock`, `sinon`, or proxyquire) are used.
